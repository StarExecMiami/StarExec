# StarExec v2.6.0

> **v2.6.0 is the first public StarExec application release since v2.4.0 and includes the
> changes prepared under the unpublished 2.5.0 and 2.5.1 source versions.**

## Why these notes are cumulative

The source tree advanced through two intermediate versions that never reached users:

| Source version | Annotated tag | Pushed to `origin` | GitHub Release |
| -------------- | ------------- | ------------------ | -------------- |
| 2.5.0          | local only    | no                 | no             |
| 2.5.1          | local only    | no                 | no             |
| 2.6.0          | this release  | expected           | expected       |

The 2.6.0 row describes the state this release is **expected** to reach once the tag is
pushed and every tag-triggered workflow has finished. It is not a claim about what exists
at the moment these notes are written; confirm it with the checklist at the end.

Because `release.yml` only fires on a pushed tag, neither 2.5.0 nor 2.5.1 was ever built or
published. Their changes are therefore included below, and anyone upgrading from **v2.4.0**
receives all three sets of changes at once.

If you maintain a clone that contains local `v2.5.0` / `v2.5.1` tags, do not push them.

## Upgrade notes for operators

Read these before upgrading a live deployment.

- **RBAC additions are required.** The Kubernetes backend now reads pod state in addition to
  job state. The chart adds the corresponding pod read permission; a deployment that pins an
  older Role will log authorization failures and be unable to observe pods.
- **Execution safety now fails closed.** Where earlier versions would proceed on ambiguous
  cluster state, StarExec now defers replacement work and retains the existing accounting.
  On a cluster with degraded API availability this is visible as work waiting rather than
  work restarting. That is the intended behaviour.
- **Admission can defer per queue.** A managed pod that cannot be accounted for now blocks
  new admission for its queue until it is resolved, instead of allowing unrelated pairs to be
  scheduled beside it.
- **A new reconciliation sweep runs periodically.** It settles ambiguous submissions, deletes
  orphaned jobs, revisits unverified executions, and inventories pods without jobs. Interval is
  configurable via `STAREXEC_K8S_ORPHAN_SWEEP_INTERVAL_MS` / `kubernetes.orphanSweepIntervalMs`
  (default `300000`).
- **Health endpoints moved into the chart's probes.** `/starexec/public/health/liveness` and
  `/starexec/public/health/readiness` are distinct: liveness reports a live process, readiness
  reports the ability to serve. Probes pointed at the old target should be updated.
- **Database migrations apply automatically on deploy** and are validated before the
  application serves traffic. See "Database migrations" below.

## Kubernetes lifecycle and execution safety (2.6.0)

Execution is treated as stopped only when both the controller and its pods are confirmed
stopped. Unknown or unobservable cluster state fails closed, so StarExec defers replacement
work and retains the accounting rather than risk two executions writing the same measurement.

Pod state is now observed alongside job state, so a pair whose pod has never started is no
longer reported as running. A pod that never starts fails its pair instead of waiting
indefinitely, and pairs are recorded against the node they actually ran on. Queues with no
nodes report why dispatch stopped rather than silently stalling.

## Rerun protocol, manual and automatic (2.6.0)

Manual reruns require the previous execution to be confirmed stopped, and report how many
pairs were actually reset rather than assuming success. Automatic reruns reset the pair and
consume the automatic-rerun allowance in one atomic step. Execution identity is revalidated
under the database row lock, so a reset cannot land on a newer execution.

## Measurement fidelity and image provenance (2.6.0)

Timeout and memory-limit classification now uses runsolver's own `TIMEOUT=` and `MEMOUT=`
verdicts instead of substring-matching its English output. All three runsolver output sources
are read, and a run whose measurements cannot be read is no longer recorded as zero — a
malformed supplemental source degrades to the sources that did parse rather than taking the
measurement down with it.

The runsolver binary is now compiled from source vendored in this repository. It was
previously downloaded from an external host at image build time with no checksum and no
pinned digest. The instrument behind every recorded measurement is now reproducible from the
tree it was audited against.

## CPU partitioning and SMT handling (2.6.0 and 2.5.0)

2.5.0 introduced generic CPU partition scheduling with a shared queue across partition
capacities. 2.6.0 makes partitioning SMT-aware: sibling threads are kept within a single
partition, and an explicit partition layout that splits siblings is rejected rather than
silently accepted.

## Database migrations (2.6.0)

Migrations are applied and validated as part of deployment. This release ships schema through
**0117**. Repeatable migrations are re-applied on each deploy; the
`job_pairs_terminal_end_time` trigger is expected to survive that re-application.

No migration in this release rewrites historical measurement rows.

## Health and readiness (2.6.0)

`/starexec/public/health/liveness` and `/starexec/public/health/readiness` are separate
endpoints so an orchestrator can distinguish a live process from one able to serve traffic.
Both are unauthenticated and safe to expose to a cluster probe.

## Disk accounting and hierarchy invariants (2.6.0)

Recording runsolver statistics is now idempotent. Repeated calls previously added the reported
figure to user and job totals each time while overwriting the stage row, leaving a surplus that
no refund could reclaim.

Moving a space into itself or into one of its own descendants is now rejected, so a space can
no longer become its own ancestor. The asynchronous benchmark upload path now satisfies the
same invariants as the synchronous one — creating the space association and charging disk
usage — so uploaded benchmarks are visible in their space and deleting them can no longer
drive recorded disk usage negative.

Read-only SQL audits for disk quota, space hierarchy, and limit misclassification are included,
along with a two-phase disk quota repair.

## Benchmark upload handling (2.5.0)

`.tar`, `.tar.gz`, and `.tgz` uploads are extracted in-process rather than via an external
`tar` subject to the global shell timeout. Extraction uses temporary `.extracting` directories
before promoting the final tree, chunk directories are cleaned up after finalization, and
partial `.assembling` files are removed on failed assembly. Cleanup targets only unfinished
temporary extraction directories, so finalized benchmark files referenced by the database are
not removed.

Tunables: `STAREXEC_UPLOAD_EXTRACTION_TIMEOUT_SECONDS` and
`STAREXEC_UPLOAD_EXTRACTION_MAX_UNCOMPRESSED_BYTES`. Expired upload source archives are cleaned
up by a background worker with retry expiry and path-safety validation.

## Description handling (2.5.1)

Primitive descriptions accept `+` and `-` consistently across server, client, XML schema, and
import paths, including URL-like scientific metadata. Job descriptions are submitted as form
data so values containing `/` round-trip correctly.

> **Interface change:** the job description edit endpoint moved from a path parameter
> (`/job/edit/description/{jobId}/{newDescription}`) to a form parameter. Any external caller
> constructing that URL directly must be updated.

## Security corrections (2.6.0 and 2.5.1)

- **Servlet authorization:** several checks reported a failure without returning, so the
  privileged work ran anyway. The most serious allowed any authenticated user to rewrite the
  queue-to-community access list.
- **StarDev transfer:** a failed StarDev login now stops the transfer instead of continuing on
  a connection that never authenticated.
- **Result recording:** a write refused because another writer already recorded a result is
  distinguished from a write that failed, so a finished pair releases its container and an
  unfinished one stays discoverable.
- **Job pair locking:** lock ordering was normalized and stored procedures that returned only
  the first matching row were repaired.
- **Description hardening (2.5.1):** pre-write import validation, contextual output encoding,
  bounded no-follow filesystem reads, and raw-description log redaction, retaining the legacy
  safety blacklist.
- **Build provenance (2.6.0):** see "Measurement fidelity and image provenance".

## CI and test coverage

Restored the pull-request checks on the `containerised` branch, cleared the OWASP
dependency-check gate, and fixed a container metadata rule that produced an invalid image
reference on non-branch events. Chart rendering is validated for every values profile, and a
check enforces that every container and init container declares the four resource fields a
namespace `ResourceQuota` requires.

## Known limitations and evidence not obtained

The validation above is a staging smoke deployment. It does **not** establish:

- readiness of a UMprod cutover — Quokka is not UMprod;
- multi-node application behaviour — the deployment is a single replica pinned to one node;
- behaviour under network partition or node loss — the fail-closed paths were not exercised
  by fault injection;
- behaviour under a full competition solver workload;
- complete measurement fidelity on real hardware — the runsolver verdict, CPU-pinning and SMT
  changes are only meaningfully exercised under real solver load;
- the absence of latent database corruption — no PANIC or checkpoint damage was observed,
  which is not the same as a verified-clean database;
- performance under production-scale concurrency.

A separate known issue, unchanged by this release: the production values profile declares a
resource shape the chart template does not consume, so the deployed application still runs on
the default limits rather than the intended production envelope. This is tracked as follow-up
work and deliberately out of scope here.

## Container images

The `v2.6.0` tag triggers publication of application-image tags `2.6.0`, `2.6`, and
`sha-<commit>`. Verify those tags and their digest after all tag-triggered workflows
complete, before pinning them.

`release.yml` and `container-publish.yml` are independent workflows that both fire on the
tag; neither waits for the other, and either can fail on its own. So the existence of this
GitHub Release does not by itself prove the images were published, and the wording above is
deliberately prospective.

The `latest` tag continues to track the `containerised` branch head and is deliberately
**not** moved by a release tag. For reproducible deployments pin `2.6.0` or, better, an
image digest.

### Post-publication checklist

Run through this once every tag-triggered workflow has finished:

- [ ] the `2.6.0` image tag exists
- [ ] the `2.6` image tag exists
- [ ] an `sha-<commit>` image tag exists for the released commit
- [ ] all three resolve to the intended digest
- [ ] `latest` did **not** move to this release
- [ ] the GitHub Release carries `starexec.war`, `starexeccommand.zip`, and `SHA256SUMS`
- [ ] both the Release workflow and the image workflow reported success
